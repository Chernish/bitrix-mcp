# bitrix-mcp

MCP-сервер, дающий ИИ-агенту **версионно-привязанный** доступ к API установленного ядра 1С-Битрикс.

Задача — убрать главную причину ошибок агента в Битрикс-разработке: уверенные утверждения об API, собранные из смеси разных версий продукта. Каждый факт, который отдаёт сервер, сопровождается модулем-владельцем и его версией.

## ⚠️ Одно требование, которое нельзя пропустить

**Индексатор запускается только с `short_open_tag=1`.**

27 652 файла ядра из 67 835 (41%) открываются коротким тегом `<?`, а не `<?php`. При выключенной настройке парсер PHP **не выдаёт ошибку** — он возвращает такой файл как HTML с нулём объявлений. Индексация завершится «успешно», а 41% ядра исчезнет из индекса молча, и сервер начнёт отвечать «не найдено» на существующие классы.

Индексатор отказывается стартовать в этом режиме (код возврата 2), а все цели `Makefile` проставляют флаг сами. Измерения — в [research.md](specs/001-bitrix-core-mcp/research.md), R-001.

## Установка

```bash
cd indexer && composer install && cd ..
cd server  && npm install && npx tsc && cd ..
```

Требуется: PHP 8.4+, Composer 2, Node 22+.

## Использование

```bash
export BITRIX_CORE_ROOT=/path/to/www/bitrix    # каталог ядра, не корень сайта
export BITRIX_MCP_INDEX=./index.sqlite

make build      # полная индексация — около 90 с на 212 МБ ядра
make update     # инкрементальная переиндексация — около 4 с
make docs       # Git-импорт официальной документации — ~25 с первый раз, ~2 с повторно
make status     # состояние индекса
make snapshots  # версии ядра и активный снимок
make verify     # сверка с контрольной выборкой
make test       # тесты индексатора и сервера
```

Подключение к агенту:

```json
{
  "mcpServers": {
    "bitrix": {
      "command": "/path/to/bitrix-mcp/bin/bitrix-mcp"
    }
  }
}
```

Launcher сам находит `index.sqlite` и production-сборку относительно корня
проекта. Другой индекс можно указать необязательной переменной
`BITRIX_MCP_INDEX`; стандартное локальное подключение её не требует.

## HTTP MCP с Bearer-авторизацией

Для сетевого доступа используется отдельный launcher `bin/bitrix-mcp-http`; локальный stdio продолжает работать без токена. HTTP-режим требует секрет длиной не менее 32 байт и отказывается стартовать без него.

```bash
export BITRIX_MCP_TOKEN="$(openssl rand -hex 32)"
export BITRIX_MCP_HTTP_HOST=127.0.0.1
export BITRIX_MCP_HTTP_PORT=3000

make server-build
make server-http
# либо: bin/bitrix-mcp-http
```

Endpoint: `POST http://127.0.0.1:3000/mcp`. В MCP-клиенте передайте заголовок, подставив секрет через его защищённое хранилище или окружение:

```text
Authorization: Bearer <BITRIX_MCP_TOKEN>
```

Токен сравнивается в constant time, не принимается через query и не пишется в логи. Запросы без него или с неверным значением получают 401 до инициализации MCP. `BITRIX_MCP_SNAPSHOT` и `--snapshot` работают и в HTTP-режиме.

По умолчанию сервер слушает только loopback. Для доступа с другой машины задайте `BITRIX_MCP_HTTP_HOST` явно и разместите сервер за **HTTPS-прокси**: передавать Bearer-токен по открытому HTTP через сеть нельзя. CORS не включён, размер JSON-запроса ограничен 1 МиБ.

## Docker и production

Корневой `Dockerfile` собирает только HTTP MCP на Node 22 и запускает его от непривилегированного пользователя. SQLite, архив снимков и версионные файлы ядра передаются через bind mount `/data`, а не вкладываются в образ.

```bash
docker build -t bitrix-mcp .
export BITRIX_MCP_TOKEN="$(openssl rand -hex 32)"

docker run --rm -p 127.0.0.1:3000:3000 \
  --mount type=bind,src="$PWD/index.sqlite",dst=/data/index.sqlite,readonly \
  --mount type=bind,src="$PWD/index.sqlite.snapshots",dst=/data/index.sqlite.snapshots,readonly \
  --mount type=bind,src="/path/to/www/bitrix",dst=/data/core,readonly \
  -e BITRIX_MCP_TOKEN \
  bitrix-mcp
```

`BITRIX_CORE_ROOT=/data/core` заменяет путь индексирующей машины для runtime-проверок `stale`. Полное ядро монтировать необязательно: достаточно `modules/main/classes/general/version.php` и всех `modules/<module>/install/version.php` с сохранением путей — остальные факты MCP читает из SQLite.

### На каком языке спрашивать

Документация Битрикса русскоязычная, а PHPDoc в коде ядра — **английский**. Поэтому `bitrix_search_docs` понимает русские запросы, а `bitrix_search_code` требует английских: «send mail», «access rights». При русском запросе к коду инструмент вернёт подсказку вместо молчаливого пустого ответа.

## Известные ограничения

**Полный PHP-исходник функции не возвращается осознанно.** Вместо выгрузки
тела `bitrix_find_callable` даёт точную сигнатуру, файл и строку, а `bitrix_find_usages` —
точки вызова. Это сохраняет контекстный бюджет и соблюдает Принцип IV.

**Параметры компонентов извлекаются неполно, и это осознанно.** Файлы `.parameters.php` — исполняемые скрипты: в них встречаются запросы к базе и вызовы `GetMessage()`. Выполнять их запрещено принципом «только чтение», поэтому вычисляемые значения помечаются `default_unresolved`, а их число отражено в `unresolved_count`. То же с ORM: замыкания в `default_value` дают `is_complete: false` с указанием причины.

**Официальная документация фиксируется по Git commit, но не по версии ядра.**
`make docs` берёт Markdown из официального
[`bitrix-tools/framework-docs`](https://github.com/bitrix-tools/framework-docs),
сохраняет SHA коммита и путь исходного файла в MCP-ответах. Примечания отдельных
возможностей вида «с версии Главного модуля 23.0.0» извлекаются вместе с
контекстом и сравниваются с версией соответствующего локального модуля.
Версии PHP и BitrixVM с ядром не смешиваются. При расхождении документации с
локальным кодом источником правды остаётся код.

**Генерированный справочник `/api/` не дублируется в индекс документации.**
Существование и сигнатуры API точнее берутся из установленного локального ядра;
`bitrix_search_docs` индексирует 199 содержательных Markdown-страниц из
официального репозитория. Аварийный HTTP-обход сайта остаётся доступен через
`php -d short_open_tag=1 indexer/bin/index.php docs --docs-source=web` и соблюдает
robots.txt, паузу и HTTP-кэш.

**Composer-зависимости модулей исключены из индекса.** 437 файлов под `modules/<модуль>/vendor/` — сторонний код (geoip2, protobuf-парсер и прочее), которому не место в справочнике по API Битрикса. Число пропущенного печатается при сборке. Каталоги `vendor` внутри `lib/` при этом индексируются: там собственный код Битрикса, например `VendorInterface` календарной синхронизации.

**`api_style` (`legacy` против `d7`) — эвристика по форме имени**, а не факт. Хранится отдельно от достоверного `is_deprecated` и помечена в ответах как догадка.

## Почему у Битрикса нет одной версии

`SM_VERSION` описывает сборку, но каждый модуль версионируется независимо и версии расходятся на целый мажор. На целевом ядре при `SM_VERSION = 25.100.300`:

```
crm     24.1300.0      rest    25.100.200
sale    24.300.0       ui      25.0.0
bizproc 24.900.0       iblock  24.300.0
```

Поэтому ответ «такой метод есть» без указания модуля и его версии недостоверен по построению: он не отвечает на вопрос «есть где».

## Версии снимков ядра

Каждый успешный `build`, `update` и `docs` публикует новый снимок в `index.sqlite.snapshots/`. Работа ведётся во временной БД; активный индекс переключается только после успешной проверки целостности. Прежние снимки остаются доступны для запросов и отката.

```bash
make snapshots                         # список и активный snapshot_id
make snapshot-archive                  # архивировать уже существующий индекс
make snapshot-use SNAPSHOT=<id>        # активировать версию
make snapshot-delete SNAPSHOT=<id>     # удалить неактивную версию

bin/bitrix-mcp --snapshot=<id>         # MCP только с выбранной версией
# либо: export BITRIX_MCP_SNAPSHOT=<id>
```

Без `--snapshot` и `BITRIX_MCP_SNAPSHOT` поведение прежнее: открывается активный `BITRIX_MCP_INDEX`. Каждый MCP-ответ содержит `snapshot_id` и `snapshot_role` (`active`, `archive`, `direct`). Хеш выбранного файла сверяется с каталогом, поэтому подменённый архив отклоняется.

Архив автоматически не очищается: каждая версия занимает размер отдельной SQLite. Удаление выполняется только явно через `snapshot-delete`; активный снимок удалить нельзя.
