# bitrix-mcp

**MCP-сервер для самостоятельного развёртывания**, который даёт ИИ-агенту справочную информацию об API **вашей установки 1С-Битрикс** с привязкой к версиям её модулей.

В репозитории — PHP-индексатор, MCP-сервер и средства их запуска. **Ядро 1С-Битрикс и готовый индекс его API в поставку не входят.** Вы разворачиваете инструмент у себя, указываете путь к собственному ядру и строите индекс для своей установки. Сервер можно использовать локально или разместить в своей инфраструктуре для доступа по HTTP.

Задача — сократить ошибки агента, возникающие из-за смешения API разных версий Битрикса. Ответы строятся по вашему индексу и содержат сведения о версии сборки, а для фактов конкретного модуля — о модуле-владельце и его версии.

## Как это работает

1. Вы предоставляете доступ к файлам своего ядра — каталогу `bitrix/` с подкаталогом `modules/`.
2. PHP-индексатор разбирает исходники и записывает сведения об API и версиях в локальный SQLite-индекс. Код ядра не исполняется, файлы Битрикса не изменяются, рабочая база сайта не используется.
3. MCP-сервер читает этот индекс и отвечает на запросы подключённого ИИ-агента через stdio или HTTP. После изменения вашего ядра индекс обновляется командой `make update`.

Набор доступных классов, модулей и методов определяется проиндексированной установкой. Официальную документацию можно дополнительно импортировать командой `make docs`.

## Установка у себя

Требуется:

- Доступ на чтение к файлам собственного ядра 1С-Битрикс на машине, где запускается индексатор.
- PHP 8.4+ с расширениями PDO и `pdo_sqlite`, Composer 2.
- Node.js 22+, npm и Make; Git — для импорта официальной документации.

Выполняйте команды из корня клонированного репозитория `bitrix-mcp`:

```bash
cd indexer && composer install && cd ..
cd server  && npm ci && npm run build && cd ..
```

### Обязательная настройка PHP

**Индексатор запускается только с `short_open_tag=1`.** В ядре встречаются файлы с коротким тегом `<?`. При выключенной настройке PHP-парсер может принять их за HTML без ошибки и пропустить объявления. На исследованной установке таких файлов было 27 652 из 67 835 (41%); доля зависит от вашей версии и состава модулей.

Индексатор отказывается стартовать без этой настройки (код возврата 2). Все цели `Makefile`, запускающие PHP, передают флаг сами. При прямом запуске используйте `php -d short_open_tag=1 indexer/bin/index.php <команда>`. Измерения — в [research.md](specs/001-bitrix-core-mcp/research.md), R-001.

## Создание индекса своей установки

Укажите абсолютный путь к **своему** каталогу `bitrix/` и путь для создаваемого индекса. `BITRIX_CORE_ROOT` нужно задать явно: пример ниже замените на путь вашей установки.

```bash
export BITRIX_CORE_ROOT=/path/to/your/site/bitrix    # каталог ядра, не корень сайта
export BITRIX_MCP_INDEX="$PWD/index.sqlite"

make build      # создать индекс API из вашего ядра
make docs       # необязательно: импортировать официальную документацию из Git
make status     # состояние индекса
```

После обновления Битрикса или изменения файлов ядра:

```bash
make update     # инкрементально обновить индекс по текущим файлам
make snapshots  # сохранённые снимки индекса и активный снимок
```

При переходе с индекса схемы 10 или более ранней на схему 11 нужен однократный `make build`: инкрементальный `update` не добавляет связи трейтов и источники зависимостей в уже созданную БД. Импортированная документация при полной пересборке сохраняется. `provenance.stale` учитывает как `SM_VERSION`, так и версии отдельных модулей. И `build`, и `update` отклоняют публикацию индекса с долей ошибок разбора выше 1%.

## Подключение к ИИ-агенту

После сборки сервера и создания индекса добавьте локальное stdio-подключение в конфигурацию MCP-клиента, заменив путь на каталог своего репозитория:

```json
{
  "mcpServers": {
    "bitrix": {
      "command": "/path/to/bitrix-mcp/bin/bitrix-mcp"
    }
  }
}
```

Launcher сам находит `index.sqlite` и production-сборку относительно корня
проекта. Другой индекс можно указать необязательной переменной
`BITRIX_MCP_INDEX`; стандартное локальное подключение её не требует.

## HTTP MCP с Bearer-авторизацией

Для сетевого доступа к развёрнутому вами серверу используется отдельный launcher `bin/bitrix-mcp-http`; локальный stdio продолжает работать без токена. Оба режима используют подготовленный вами индекс. HTTP-режим требует секрет длиной не менее 32 байт и отказывается стартовать без него.

```bash
export BITRIX_MCP_TOKEN="$(openssl rand -hex 32)"
export BITRIX_MCP_HTTP_HOST=127.0.0.1
export BITRIX_MCP_HTTP_PORT=3000

make server-build
make server-http
# либо: bin/bitrix-mcp-http
```

Endpoint: `POST http://127.0.0.1:3000/mcp`. В MCP-клиенте передайте заголовок, подставив секрет через его защищённое хранилище или окружение:

```text
Authorization: Bearer <BITRIX_MCP_TOKEN>
```

Токен сравнивается в constant time, не принимается через query и не пишется в логи. Запросы без него или с неверным значением получают 401 до инициализации MCP. `BITRIX_MCP_SNAPSHOT` и `--snapshot` работают и в HTTP-режиме.

По умолчанию сервер слушает только loopback. Для доступа с другой машины задайте `BITRIX_MCP_HTTP_HOST` явно и разместите сервер за **HTTPS-прокси**: передавать Bearer-токен по открытому HTTP через сеть нельзя. CORS не включён, размер JSON-запроса ограничен 1 МиБ.

## Docker и production

Корневой `Dockerfile` собирает HTTP MCP-сервер на Node 22 и запускает его от непривилегированного пользователя. PHP-индексатор и ядро Битрикса в образ не входят. Сначала создайте индекс своего ядра командами выше на машине с PHP; затем передайте SQLite, каталог снимков индекса и файлы своего ядра в контейнер через bind mount `/data`.

```bash
docker build -t bitrix-mcp .
export BITRIX_MCP_TOKEN="$(openssl rand -hex 32)"

docker run --rm -p 127.0.0.1:3000:3000 \
  --mount type=bind,src="$PWD/index.sqlite",dst=/data/index.sqlite,readonly \
  --mount type=bind,src="$PWD/index.sqlite.snapshots",dst=/data/index.sqlite.snapshots,readonly \
  --mount type=bind,src="/path/to/your/site/bitrix",dst=/data/core,readonly \
  -e BITRIX_MCP_TOKEN \
  bitrix-mcp
```

В примере используются `index.sqlite` и `index.sqlite.snapshots/`, созданные вами в корне репозитория. Все источники bind mount должны существовать на Docker-хосте; при переносе сервера скопируйте туда индекс и каталог его снимков.

Заданная в образе переменная `BITRIX_CORE_ROOT=/data/core` заменяет путь индексирующей машины для runtime-проверок `stale`. Для этих проверок достаточно предоставить актуальные файлы версий вашей установки: `modules/main/classes/general/version.php` и `modules/<module>/install/version.php` для остальных модулей с сохранением путей. Остальные факты MCP читает из SQLite. Для построения и обновления индекса PHP-индексатору по-прежнему нужны исходники вашего ядра.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `bitrix_find_symbol` | найти класс, интерфейс, трейт по имени; разрешает `class_alias` |
| `bitrix_get_class` | методы класса с точными сигнатурами, постранично |
| `bitrix_check_method` | точная проверка метода с учётом наследования и трейтов; возвращает фактическое объявление через `declared_in`, различает «нет класса» и «нет метода» |
| `bitrix_get_orm_entity` | схема ORM-сущности: таблица, поля, типы, связи; помечает неполноту |
| `bitrix_list_events` | события модуля; отдельно те, что модуль бросает, и те, на что подписан |
| `bitrix_get_component` | параметры компонента; помечает значения, вычисляемые в рантайме |
| `bitrix_list_rest_methods` | REST-методы, публикуемые модулями |
| `bitrix_search_docs` | поиск по официальной документации **по-русски**; возвращает примечания «с версии» и их применимость к локальным модулям |
| `bitrix_search_code` | поиск по коду по описанию задачи **по-английски**; полные совпадения выше частичных |
| `bitrix_list_modules` | модули и их независимые версии |
| `bitrix_get_module` | структура, зависимости и счётчики API модуля |
| `bitrix_list_module_api` | классы, интерфейсы, трейты, enum и функции модуля |
| `bitrix_list_components` | поиск и постраничный список компонентов |
| `bitrix_get_class_hierarchy` | цепочка наследования и прямые интерфейсы |
| `bitrix_get_class_constants` | константы класса и AST-представления значений |
| `bitrix_find_implementations` | классы, реализующие интерфейс, включая встроенные PHP-интерфейсы |
| `bitrix_list_data_managers` | список ORM DataManager-сущностей |
| `bitrix_find_events` | поиск событий и обработчиков по всему ядру |
| `bitrix_find_callable` | точный поиск функции/метода с сигнатурой и фильтром модуля |
| `bitrix_find_usages` | AST-точки вызова функции или метода; динамические цели помечаются |
| `bitrix_get_doc_page` | чтение официальной страницы порциями с примечаниями «с версии» |
| `bitrix_find_namespace` | классы и функции в заданном PHP namespace |
| `bitrix_index_status` | состояние индекса, счётчики, признаки устаревания и непригодности |

Аргументы каждого MCP-вызова проверяются по опубликованной `inputSchema`: обязательные поля, типы, enum и отсутствие неизвестных полей. `limit` — целое положительное число с ограничением, указанным в схеме инструмента; `offset` — целое неотрицательное. Невалидный вызов возвращает `isError: true`, а не данные другого API.

Каждый успешный ответ несёт блок `provenance`: версия сборки, идентификатор снимка индекса и признак `stale`; для фактов конкретного модуля — также модуль и его версия.

### На каком языке спрашивать

Документация Битрикса русскоязычная, а PHPDoc в коде ядра — **английский**. Поэтому `bitrix_search_docs` понимает русские запросы, а `bitrix_search_code` требует английских: «send mail», «access rights». При русском запросе к коду инструмент вернёт подсказку вместо молчаливого пустого ответа.

## Известные ограничения

**Полный PHP-исходник функции не возвращается осознанно.** Вместо выгрузки
тела `bitrix_find_callable` даёт точную сигнатуру, файл и строку, а `bitrix_find_usages` —
точки вызова. Это сохраняет контекстный бюджет и соблюдает Принцип IV.

**Параметры компонентов извлекаются неполно, и это осознанно.** Файлы `.parameters.php` — исполняемые скрипты: в них встречаются запросы к базе и вызовы `GetMessage()`. Выполнять их запрещено принципом «только чтение», поэтому вычисляемые значения помечаются `default_unresolved`, а их число отражено в `unresolved_count`. То же с ORM: замыкания в `default_value` дают `is_complete: false` с указанием причины.

**Официальная документация фиксируется по Git commit, но не по версии ядра.**
`make docs` берёт Markdown из официального
[`bitrix-tools/framework-docs`](https://github.com/bitrix-tools/framework-docs),
сохраняет SHA коммита и путь исходного файла в MCP-ответах. Примечания отдельных
возможностей вида «с версии Главного модуля 23.0.0» извлекаются вместе с
контекстом и сравниваются с версией соответствующего локального модуля.
Версии PHP и BitrixVM с ядром не смешиваются. При расхождении документации с
локальным кодом источником правды остаётся код.

**Генерированный справочник `/api/` не дублируется в индекс документации.**
Существование и сигнатуры API точнее берутся из установленного локального ядра;
`make docs` импортирует содержательные Markdown-страницы из официального
репозитория для поиска через `bitrix_search_docs` (199 страниц в контрольном прогоне). Аварийный HTTP-обход сайта остаётся доступен через
`php -d short_open_tag=1 indexer/bin/index.php docs --docs-source=web` и соблюдает
robots.txt, паузу и HTTP-кэш.

**Composer-зависимости модулей исключены из индекса.** Файлы под `modules/<модуль>/vendor/` — сторонний код (geoip2, protobuf-парсер и прочее), которому не место в справочнике по API Битрикса. На контрольной установке исключено 437 файлов; число пропущенного печатается при сборке. Каталоги `vendor` внутри `lib/` при этом индексируются: там собственный код Битрикса, например `VendorInterface` календарной синхронизации.

**`api_style` (`legacy` против `d7`) — эвристика по форме имени**, а не факт. Хранится отдельно от достоверного `is_deprecated` и помечена в ответах как догадка.

## Почему у Битрикса нет одной версии

`SM_VERSION` описывает сборку, но каждый модуль версионируется независимо и версии могут расходиться на целый мажор. Например, на контрольной установке при `SM_VERSION = 25.100.300`:

```
crm     24.1300.0      rest    25.100.200
sale    24.300.0       ui      25.0.0
bizproc 24.900.0       iblock  24.300.0
```

Поэтому ответ «такой метод есть» без указания модуля и его версии недостоверен по построению: он не отвечает на вопрос «есть где».

## Снимки индекса и выбор версии API

Снимок — это SQLite-файл с извлечёнными сведениями об API, версиями модулей и импортированной документацией. **Снимки не содержат дистрибутив ядра и не устанавливают или откатывают Битрикс.** Они позволяют агенту обращаться к ранее проиндексированным состояниям вашей установки.

Каждый успешный `build`, `update` и `docs` сохраняет новый снимок индекса в `index.sqlite.snapshots/` (для другого `BITRIX_MCP_INDEX` — в `<путь_индекса>.snapshots/`). Работа ведётся во временной БД; активный индекс переключается только после успешной проверки целостности. Прежние снимки остаются доступны для запросов и переключения MCP на предыдущий индекс.

```bash
make snapshots                          # список и активный snapshot_id
make snapshot-archive                   # архивировать уже существующий индекс
make snapshot-use SNAPSHOT="<id>"        # активировать сохранённый индекс
make snapshot-delete SNAPSHOT="<id>"     # удалить неактивный снимок индекса

bin/bitrix-mcp --snapshot="<id>"          # MCP только с выбранным снимком индекса
# либо: export BITRIX_MCP_SNAPSHOT="<id>"
```

Замените `<id>` на идентификатор из `make snapshots`. Без `--snapshot` и `BITRIX_MCP_SNAPSHOT` сервер открывает активный `BITRIX_MCP_INDEX`. Каждый успешный MCP-ответ содержит `snapshot_id` и `snapshot_role` (`active`, `archive`, `direct`). Хеш выбранного файла сверяется с каталогом, поэтому подменённый архив отклоняется.

Архив автоматически не очищается: каждый снимок занимает размер отдельной SQLite. Удаление выполняется только явно через `snapshot-delete`; активный снимок удалить нельзя.
