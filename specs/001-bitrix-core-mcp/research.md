## R-001. Короткие открывающие теги ломают индексацию молча (КРИТИЧНО)

**Решение**: индексатор MUST выполняться с `short_open_tag=On` и MUST отказываться стартовать, если настройка выключена.

**Измерение**. В ядре 27 652 PHP-файла (41% от 67 835) открываются коротким тегом `<?`, а не `<?php`. Прогон php-parser 5.8.0 на выборке 3000 файлов:

| Режим | Успешно | Ошибок разбора | Съедено молча | Классов найдено |
|---|---|---|---|---|
| `short_open_tag=Off` | 98.43% | 47 (1.57%) | **2122** | 904 |
| `short_open_tag=On` | **100%** | **0** | **0** | **1058** |

**Почему это критично**. При `Off` парсер не выдаёт ошибку. Он возвращает файл как единственный узел `Stmt\InlineHTML` — синтаксически корректный результат, содержащий ноль объявлений. Индексатор счёл бы такой файл успешно обработанным и пустым. В выборке так терялось 70% файлов и 15% классов.

Это прямое нарушение сразу двух принципов конституции: III («молчаливая потеря данных ЗАПРЕЩЕНА») и I — потому что символ, существующий в ядре, отдавался бы как «не найдено», превращая честный отказ в ложь.

**Как обеспечить**. `short_open_tag` — настройка INI, влияющая на `token_get_all()`; php-parser не может её эмулировать. Поэтому:

1. Точка входа индексатора MUST проверять `ini_get('short_open_tag')` и аварийно завершаться с внятным сообщением, если она выключена.
2. Штатный запуск MUST передавать `-d short_open_tag=1` явно, не полагаясь на php.ini машины.
3. Регрессионный тест MUST содержать файл с коротким тегом и проверять, что класс из него найден.

Замеренная в этом окружении настройка по умолчанию — `Off`, то есть без явных мер дефект возник бы сразу.

**Альтернативы отвергнуты**: предобработка `<?` → `<?php` перед разбором сдвигает смещения и ломает номера строк (нарушение FR-004); tree-sitter-php не даёт семантики PHP и запрещён Принципом III.

## R-002. Параллелизм индексатора не нужен

**Решение**: индексатор — один процесс, последовательный обход. Параллелизм не закладывать.

**Измерение**. Пропускная способность при `short_open_tag=On`: 952 файла/с, 4.1 МБ/с (разбор + `NameResolver` + обход дерева). Реальный объём ядра — 212.2 МБ в 67 836 файлах, средний файл 3.2 КБ. Отсюда чистый разбор всего ядра — **около 52 секунд в один поток**. Выборка для замера состояла из файлов размером 4.3 КБ, то есть была тяжелее среднего, поэтому оценка консервативна.

**Почему так**. Исходное опасение (в задании на планирование) состояло в том, что 67 836 файлов последовательно займут неприемлемо долго. Измерение это опровергает: с учётом извлечения сущностей и записи в SQLite полная индексация укладывается в единицы минут, что для операции, выполняемой при обновлении ядра, приемлемо.

**Почему не делать параллельно**. Многопроцессная запись в один файл SQLite требует либо координатора-писателя, либо слияния частичных БД. И то и другое усложняет достижение детерминированности, которую требует Принцип V. Платить этой сложностью за экономию порядка минуты нельзя.

**Запасной вариант**, если после реализации извлечения полный прогон превысит 10 минут: пул воркеров, разбирающих файлы и отдающих сериализованные записи одному процессу-писателю. Порог зафиксирован здесь, чтобы решение принималось по измерению, а не по ощущению.

## R-003. Карты полей ORM существуют в двух формах, обе разбираемы статически

**Решение**: поддержать обе формы, различать их и помечать неразрешённые части.

**Измерение**: 1463 файла содержат `getMap()`, из них 504 используют fluent-стиль. `array_merge(parent::getMap(), ...)` встречается всего в 6 файлах.

**Форма A — литеральный массив** (преобладает):

```php
'ID' => ['data_type' => 'integer', 'primary' => true, 'autocomplete' => true],
'IBLOCK_TYPE_ID' => ['data_type' => 'string', 'required' => true, 'validation' => function() {...}],
```

Ключи и значения `data_type`, `primary`, `required`, `autocomplete` — литералы, извлекаются целиком.

**Форма B — объекты полей с цепочкой конфигурации**:

```php
(new IntegerField('ID'))->configurePrimary(true)->configureAutocomplete(true),
(new Reference('IMAGE', \Bitrix\Main\FileTable::class, Join::on('this.IMAGE_ID', 'ref.ID'))),
(new EnumField('MESSAGE_TYPE', ['values' => ['text', 'html']]))->configureDefaultValue('text'),
```

Имя поля — первый строковый аргумент конструктора, тип — имя класса поля, конфигурация — цепочка `configureXxx()`. Связь `Reference` даёт целевую сущность через `::class` и условие соединения. Всё это узлы AST, извлекается без выполнения кода.

**Что не извлекается**: `default_value` и `validation`, заданные замыканиями. Их MUST помечать как неразрешённые, а сущность — как частично извлечённую (Принцип III). Значение замыкания для агента почти бесполезно, а вот ложное «поле без значения по умолчанию» вредно.

## R-004. Параметры компонентов не декларативны — извлечение заведомо частичное

**Решение**: извлекать статически определимую структуру, каждое вычисляемое значение помечать как неразрешённое. Файлы НЕ выполнять.

**Наблюдение**. `.parameters.php` — это исполняемый скрипт, а не манифест. Реальный пример из `components/bitrix/main.feedback/.parameters.php`:

```php
$arEvent = array();
$dbType = CEventMessage::GetList("id", "desc", $arFilter);   // запрос к БД
while ($arType = $dbType->GetNext()) { ... }

$arComponentParameters = array("PARAMETERS" => array(
    "USE_CAPTCHA" => Array("NAME" => GetMessage("MFP_CAPTCHA"), "TYPE" => "CHECKBOX", "DEFAULT" => "Y"),
    "EMAIL_TO"    => Array("DEFAULT" => htmlspecialcharsbx(COption::GetOptionString("main", "email_from"))),
));
```

Здесь `TYPE`, `PARENT`, литеральные `DEFAULT` и список `VALUES` извлекаются. А `GetMessage(...)` (перевод) и `COption::GetOptionString(...)` (значение из БД) вычисляются в рантайме.

**Последствие Принципа VI**. Конституция прямо запрещает выполнять код ядра и обращаться к рабочей БД. Значит полнота извлечения параметров компонентов принципиально недостижима, и это не дефект реализации, а следствие осознанного архитектурного выбора. Такие поля MUST отдаваться с признаком «вычисляется в рантайме» вместо подстановки пустого значения.

**Масштаб**: 2414 файлов `.parameters.php` и 2320 `.description.php`.

**Альтернатива отвергнута**: выполнение файлов в песочнице с заглушками Битрикса. Это нарушило бы Принцип VI, привнесло бы состояние рабочего приложения и разрушило детерминированность из Принципа V.

## R-005. События извлекаются из строковых литералов

**Решение**: извлекать оба поколения API по узлам вызовов.

Старое API — `GetModuleEvents("vote", "onBeforeVoteDelete")`, D7 — `new Event('sale', 'OnSaleDiscountPresetBuildList')`. В обоих случаях модуль и имя события заданы строковыми литералами в фиксированных позициях аргументов, что даёт надёжное извлечение через AST.

Дополнительно покрываются `ExecuteModuleEventEx` и отправка через `EventManager`. Регистрации обработчиков (`registerEventHandler`) индексируются отдельным видом записи, чтобы отличать «кто вызывает событие» от «кто на него подписан».

## R-006. Псевдонимы классов обязательны к индексации

**Решение**: `class_alias` индексируется отдельной таблицей, поиск символа MUST разрешать псевдонимы.

**Измерение**: 144 вызова `class_alias` в ядре. Примеры:

```php
class_alias('\Bitrix\Sale\Internals\OrderTable', '\Bitrix\Sale\OrderTable');
class_alias('\Bitrix\Sale\Internals\FuserTable', '\Bitrix\Sale\FuserTable');
```

**Почему важно**. `\Bitrix\Sale\OrderTable` — именно та форма, которую агент напишет и по которой будет искать, но объявления с таким именем в ядре нет: класс объявлен как `\Bitrix\Sale\Internals\OrderTable`. Без индексации псевдонимов система ответила бы «не найдено» на существующий и повсеместно используемый класс — то есть ровно тот отказ, который Принцип I требует давать только для действительно отсутствующих сущностей.

Ответ по псевдониму MUST указывать и запрошенное имя, и каноническое.

## R-007. Признак устаревшего API — три независимых сигнала

**Решение**: помечать устаревание по совокупности сигналов, каждый хранить отдельно.

1. **`@deprecated` в PHPDoc** — 751 файл. Самый достоверный сигнал, часто содержит указание на замену.
2. **Классы `CAll*`** — 184 объявления. Базовые классы старого процедурного API.
3. **Эвристика имени**: класс вне пространства имён, имя начинается с `C` и заглавной буквы (`CCrmDeal`, `CIBlockElement`) — старое API; класс в пространстве `Bitrix\` — D7.

Третий сигнал — эвристика, поэтому он MUST храниться как отдельный признак `api_style`, а не смешиваться с достоверным `is_deprecated` из PHPDoc. Смешение нарушило бы Принцип III: догадка не должна быть неотличима от факта.

## R-008. Хранилище: FTS5 доступен на обеих сторонах

**Решение**: SQLite с FTS5; запись из PHP через PDO, чтение из Node через `better-sqlite3`.

**Проверено**:

| Сторона | SQLite | FTS5 | trigram | unicode61 |
|---|---|---|---|---|
| PHP 8.4.4 (PDO) | 3.51.1 | ✓ | ✓ | ✓ |
| Node 22.21 (`node:sqlite`) | 3.50.4 | ✓ | ✓ | — |

**Выбор драйвера для сервера**: `better-sqlite3`. Встроенный `node:sqlite` работает и не требует флага, но помечен экспериментальным с оговоркой «API может измениться в любой момент» — это неприемлемый риск сопровождения для инструмента, который планируется использовать долго. `better-sqlite3` даёт стабильный синхронный API, точно ложащийся на модель «запрос-ответ» MCP. Цена — сборка нативного модуля при установке.

**Расхождение версий SQLite** (запись 3.51.1, чтение 3.50.4) допустимо: формат файла и FTS5 совместимы снизу вверх в этом диапазоне. Зафиксировано как известное условие, требующее перепроверки при смене окружения.

**Стратегия поиска разделена по природе данных**:

- **Точный лукап по именам** (класс, метод, событие) — обычные B-tree индексы по колонкам в нижнем регистре. Полнотекстовый поиск здесь хуже: для идентификаторов важно точное и префиксное совпадение, а не морфология.
- **Документация на русском** — FTS5 с токенизатором `unicode61`, что закрывает требование FR-032 о кириллице.
- **PHPDoc и поиск по описанию задачи** — отдельная FTS5-таблица над комментариями и сигнатурами.

## R-009. Обнаружение рассинхрона индекса и ядра

**Решение**: трёхуровневая проверка, от самой дешёвой к самой полной.

1. **Дешёвая, на каждый запрос**: сверка `SM_VERSION` из `modules/main/classes/general/version.php` с записанной в снимке. Одно чтение файла.
2. **Средняя, по таймеру или явному запросу**: перечитывание 99 файлов версий модулей и сверка карты версий.
3. **Полная, только при переиндексации**: обход дерева со сверкой размера и времени модификации, затем хеша при расхождении.

Первый уровень ловит штатное обновление Битрикса, которое всегда меняет `SM_VERSION`. Он не ловит ручную правку файла ядра, но такая правка нарушает саму модель поставки и относится к сценарию, для которого предусмотрена переиндексация.

Признак устаревания MUST попадать в каждый ответ инструмента, а не только в отдельную диагностическую команду — иначе агент, не спросивший о состоянии индекса, получит устаревший факт без предупреждения (Принцип II).

## R-010. Инкрементальность

**Решение**: `(размер, mtime)` как быстрый фильтр, SHA-256 как арбитр.

Обход сравнивает размер и время модификации с сохранёнными. При совпадении файл пропускается без чтения. При расхождении файл читается, считается SHA-256, и только при отличии хеша запись перестраивается — это защищает от лишней работы при обновлениях, меняющих время модификации без изменения содержимого.

Удаление реализуется через пометку всех файлов снимка признаком «не встречен» перед обходом и удалением непомеченных после. Каскадное удаление зависимых записей по внешнему ключу `file_id`.

Карта версий модулей перечитывается **всегда и целиком**, независимо от инкрементальности: она дешёвая (99 файлов) и критична для Принципа II.

## R-011. Сбор документации

**Решение**: прямые HTTP-запросы из кода индексатора, обход по `sitemap.xml`.

**Проверено**: `robots.txt` сайта `docs.1c-bitrix.ru` запрещает только `/_search/`; `sitemap.xml` доступен и содержит 112 URL в разделах framework (36), get-started (19), orm (15), cms-basics (13), security (12), database (8), performance (6).

**Ограничение окружения**: штатный механизм загрузки веб-страниц агента к этому домену блокируется корпоративной сетевой политикой, тогда как прямые HTTP-запросы проходят. Поэтому краулер реализуется в коде индексатора и не может опираться на инструментарий агента.

Кэширование по `ETag` и SHA-256 содержимого, пауза между запросами. При 112 страницах полный обход занимает секунды, поэтому сложные стратегии обхода не нужны.

## R-012. Транспорт MCP и чистота stdout

**Решение**: stdio; stdout принадлежит исключительно протоколу.

При транспорте stdio любой посторонний вывод в stdout ломает поток сообщений протокола. Отсюда требование: диагностика, предупреждения и логи сервера MUST направляться в stderr. Это же соображение — дополнительный аргумент против `node:sqlite`, который печатает предупреждение об экспериментальном статусе (оно идёт в stderr и потому безвредно, но лишний источник вывода в процессе-сервере нежелателен).

## R-013. Поправки, найденные при реализации

Два факта, записанных в фазе 0 со слов первичной разведки, не подтвердились на реальном ядре. Обнаружены прогоном `ModuleVersionReader` против `/Users/sergejcernomordov/stroka/bp/www/bitrix`; исправлены во всех документах.

**Расположение константы версии сборки.** Записано было `modules/main/install/version.php`. Такого файла в ядре **нет**. `SM_VERSION` и `SM_VERSION_DATE` объявлены в `modules/main/classes/general/version.php`. Главный модуль — единственное исключение по расположению: у остальных модулей версия лежит в `install/version.php` в виде массива.

Цена ошибки была бы неприятной и тихой: `readBuildVersion()` возвращал бы `null`, версия сборки в снимке оказалась бы пустой, а `main` получил бы статус «версия неизвестна» — то есть главный модуль ядра остался бы без атрибуции при формально работающем индексаторе.

**Число модулей.** Записано было 99, фактически **93**. Первый замер выполнялся как подсчёт элементов каталога `modules`, куда попали `updater.log`, `updater_partner.log`, `install.log` и `.htaccess`. Достоверный способ — считать только каталоги.

Проверка на реальном ядре после исправления: 93 модуля, **ни одного без версии**, `main@25.100.300` с источником `sm_version`, остальные с источником `module_file`.

**Вывод для остальных фаз**: измерения, полученные подсчётом элементов каталога, требуют перепроверки типом элемента. Обнаружено это только потому, что ридер версий проверялся на настоящем ядре, а не только на фикстурах, — практику стоит сохранить для всех последующих визиторов.
