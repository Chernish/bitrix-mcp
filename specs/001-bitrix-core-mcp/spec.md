# Feature Specification: MCP-сервер по ядру 1С-Битрикс с версионной привязкой

**Feature Branch**: `001-bitrix-core-mcp`

**Created**: 2026-08-12

**Status**: Draft

**Input**: User description: MCP-сервер для разработки под 1С-Битрикс, дающий ИИ-агенту точный, версионно-привязанный доступ к API локального ядра Битрикса (`/Users/sergejcernomordov/stroka/bp/www/bitrix`, SM_VERSION 25.100.300, 93 модуля, 67 836 PHP-файлов) и к концептуальной документации `docs.1c-bitrix.ru` (112 страниц).

## Постановка проблемы

ИИ-агент, пишущий код под 1С-Битрикс, систематически ошибается в API: предлагает методы, которых нет в конкретной сборке, путает старое процедурное API (`CCrmDeal`, `CIBlockElement`) с D7 (`\Bitrix\Crm\...`), выдумывает поля ORM-сущностей и имена событий. Причина — обучающие данные смешивают разные версии Битрикса, а сам продукт не имеет единой версии: `SM_VERSION` описывает сборку, но каждый модуль версионируется независимо и версии разъезжаются на целый мажор. В целевом ядре одновременно живут `crm@24.1300.0`, `rest@25.100.200`, `bizproc@24.900.0`, `ui@25.0.0`, `sale@24.300.0`.

Следствие: любой ответ об API без указания модуля и его версии недостоверен. Нужен источник правды, привязанный к конкретной установленной сборке.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Точная сигнатура API ядра с версионной привязкой (Priority: P1)

Разработчик через ИИ-агента пишет код под Битрикс и должен вызвать метод ядра. Агент спрашивает у MCP имя класса или метода и получает точную сигнатуру ровно в том виде, в каком она существует в установленной сборке, с указанием модуля-владельца, его версии, пути к файлу и номера строки.

**Why this priority**: Это устраняет главную причину ошибок агента. Без этой истории остальные не имеют смысла — все прочие сценарии являются надстройками над индексом символов ядра. Одна эта история уже даёт работоспособный MVP.

**Independent Test**: Взять контрольную выборку из существующих классов и методов ядра, задать по ним вопросы инструменту и сверить каждый ответ с исходником — сигнатура, модуль, версия, путь и строка должны совпасть.

**Acceptance Scenarios**:

1. **Given** индекс построен по ядру с SM_VERSION 25.100.300, **When** агент запрашивает класс из модуля `crm`, **Then** возвращаются сигнатуры его методов с явным указанием `crm@24.1300.0`, пути к файлу и номера строки.
2. **Given** в ядре есть несколько классов с одинаковым коротким именем в разных модулях, **When** агент ищет по короткому имени, **Then** возвращаются все совпадения, разделённые по модулям, с версией каждого.
3. **Given** запрошенного метода в текущей сборке нет, **When** агент его запрашивает, **Then** система отвечает явным «не найдено в этой сборке» и не предлагает догадок.
4. **Given** класс относится к устаревшему процедурному API, **When** агент его запрашивает, **Then** ответ помечает его как устаревший и, если известен, указывает D7-аналог.

### User Story 2 — ORM-схема сущности (Priority: P2)

Агент собирается читать или писать данные через ORM и должен знать точный состав сущности: имя таблицы, поля, их типы, обязательность и связи с другими сущностями.

**Why this priority**: Работа с данными — самая частая задача в Битрикс-разработке, и выдуманные имена полей ломают код молча, без ошибки на этапе написания. Ценность высокая, но история опирается на индекс символов из US1.

**Independent Test**: Запросить схемы у выборки ORM-сущностей разных модулей и сверить поля и типы с содержимым `getMap()` в исходниках.

**Acceptance Scenarios**:

1. **Given** индекс построен, **When** агент запрашивает ORM-схему сущности, **Then** возвращаются имя таблицы, список полей с типами, признаком обязательности и описанием связей, с указанием модуля и версии.
2. **Given** карта полей сущности собирается динамически и не определима статически целиком, **When** агент запрашивает её схему, **Then** возвращается статически извлечённая часть с явной пометкой о неполноте.

---

### User Story 3 — События модуля (Priority: P2)

Агент должен повесить обработчик на событие Битрикса и нуждается в точном имени события, модуле, который его вызывает, и сигнатуре обработчика.

**Why this priority**: Имена событий — вторая по частоте категория галлюцинаций после имён методов, и найти их вручную в 67 тысячах файлов дорого.

**Independent Test**: Запросить список событий у выборки модулей и сверить с точками вызова в исходниках.

**Acceptance Scenarios**:

1. **Given** индекс построен, **When** агент запрашивает события модуля, **Then** возвращается список имён событий с точкой вызова (файл и строка), передаваемыми параметрами, модулем и версией.
2. **Given** событие вызывается из нескольких мест, **When** агент его запрашивает, **Then** перечисляются все точки вызова.

---

### User Story 4 — Инкрементальная переиндексация после обновления ядра (Priority: P2)

Разработчик обновил Битрикс штатным апдейтером. Он запускает одну команду, и индекс приводится в соответствие с новой сборкой, переобрабатывая только изменившееся.

**Why this priority**: Без этого индекс устаревает и начинает врать — то есть ровно та проблема, ради которой всё делалось, возвращается. Полная индексация из US1 уже работает, эта история делает поддержание индекса дешёвым.

**Independent Test**: Построить индекс, изменить несколько файлов ядра и удалить один, запустить переиндексацию, убедиться, что изменения отражены, удалённые записи исчезли, а время работы существенно меньше полной индексации.

**Acceptance Scenarios**:

1. **Given** индекс построен, **When** запускается переиндексация без изменений в ядре, **Then** она завершается заметно быстрее полной и содержимое индекса не меняется.
2. **Given** часть файлов изменилась, **When** запускается переиндексация, **Then** обновляются только записи изменившихся файлов, а карта версий модулей и SM_VERSION перечитываются заново.
3. **Given** файл удалён из ядра, **When** запускается переиндексация, **Then** связанные с ним записи удаляются из индекса.
4. **Given** SM_VERSION ядра изменился с момента индексации, **When** агент обращается к любому инструменту, **Then** ответ содержит предупреждение о рассинхроне индекса и ядра.

---

### User Story 5 — Параметры компонентов и REST-методы (Priority: P3)

Агент подключает компонент Битрикса или вызывает REST-метод и нуждается в списке поддерживаемых параметров либо в перечне методов, которые модуль публикует наружу.

**Why this priority**: Ценно, но применяется реже, чем работа с классами, ORM и событиями, и обходной путь (заглянуть в `.parameters.php`) дешевле.

**Independent Test**: Запросить параметры выборки компонентов и списки REST-методов у модулей, сверить с исходниками.

**Acceptance Scenarios**:

1. **Given** индекс построен, **When** агент запрашивает параметры компонента по идентификатору вида `namespace:name`, **Then** возвращается список параметров с типами и значениями по умолчанию, с указанием модуля и версии.
2. **Given** модуль публикует REST-методы, **When** агент запрашивает их список, **Then** возвращаются имена методов и обработчики, к которым они привязаны.

---

### User Story 6 — Поиск по концептуальной документации (Priority: P3)

Агенту нужен не сигнатурный факт, а понимание подхода: как правильно работать с ORM, какие есть требования безопасности, как устроен кеш. Он ищет по документации и получает релевантные фрагменты со ссылками на источник.

**Why this priority**: Отвечает на вопросы «как правильно», которых нет в коде, но объём источника невелик (112 страниц) и он не привязан к версиям, поэтому ценность ниже, чем у кодового индекса.

**Independent Test**: Задать вопросы по темам разделов документации и проверить, что возвращаются релевантные фрагменты с рабочими ссылками на исходные страницы.

**Acceptance Scenarios**:

1. **Given** документация проиндексирована, **When** агент делает запрос на естественном языке по-русски, **Then** возвращаются релевантные фрагменты с заголовком, разделом и URL исходной страницы.
2. **Given** документация утверждает наличие метода, которого нет в индексе кода, **When** агент запрашивает этот метод, **Then** приоритет отдаётся коду и расхождение явно отмечено в ответе.
3. **Given** сайт документации недоступен, **When** запускается сбор документации, **Then** сбор завершается с внятной ошибкой, а ранее собранный кэш и индекс кода продолжают работать.

---

### Edge Cases

- **Модуль без файла версии.** У `main` версия задаётся как `SM_VERSION`, а не как массив версии модуля; часть модулей может не иметь файла версии вовсе. Сущность всё равно должна получить атрибуцию к модулю, а версия — быть помечена как неизвестная, а не подставлена наугад.
- **Одноимённые классы в разных модулях.** В ядре это норма; поиск по короткому имени обязан возвращать все варианты, а не первый попавшийся.
- **Непарсибельные и смешанные файлы.** В ядре есть шаблоны с перемешанными HTML и PHP, файлы с синтаксисом старых версий PHP и намеренно битые фикстуры. Обход не должен на них падать.
- **Динамические карты ORM.** Часть `getMap()` строит поля через условия и вызовы; статически извлекается не всё, и неполнота должна быть видна потребителю.
- **Ядро переехало или недоступно.** Настроенный путь может стать невалидным; сообщение должно указывать на конкретную причину.
- **Слишком общий поисковый запрос.** Запрос вроде «user» даёт сотни совпадений; выдача должна быть ограничена, ранжирована и сопровождаться подсказкой о сужении.
- **Очень большой класс.** Классы старого API содержат десятки методов; ответ обязан оставаться компактным и поддерживать постраничный запрос.
- **Кириллица в поисковых запросах.** Документация русскоязычная, полнотекстовый поиск обязан корректно работать с кириллицей и словоформами.
- **Смена структуры сайта документации.** Разбор страниц может перестать соответствовать разметке; сбой сбора документации не должен ломать кодовую часть.

## Requirements *(mandatory)*

### Functional Requirements

#### Индексация ядра

- **FR-001**: Система MUST обходить дерево модулей ядра и извлекать классы, интерфейсы и трейты с полным разрешением пространств имён и импортов.
- **FR-002**: Система MUST извлекать сигнатуры методов: имя, видимость, признаки статичности и абстрактности, параметры с типами, значениями по умолчанию, признаками передачи по ссылке и вариативности, а также тип возвращаемого значения.
- **FR-003**: Система MUST сохранять документирующие комментарии символов и признак устаревшего API.
- **FR-004**: Система MUST фиксировать для каждой извлечённой сущности путь к файлу и номер строки.
- **FR-005**: Система MUST определять модуль-владелец каждой сущности и его версию, читая файл версии модуля, а для главного модуля — константу версии сборки.
- **FR-006**: Система MUST записывать метаданные снимка: версию сборки, дату версии, полную карту «модуль → версия», время индексации и абсолютный путь корня индексации.
- **FR-007**: Система MUST извлекать ORM-сущности: классы-наследники менеджера данных, имя таблицы и карту полей с типами, обязательностью и связями.
- **FR-008**: Система MUST извлекать события: имена, модули, точки вызова и передаваемые параметры.
- **FR-009**: Система MUST извлекать компоненты: идентификатор, параметры и описание.
- **FR-010**: Система MUST извлекать REST-методы, публикуемые модулями.
- **FR-011**: Система MUST извлекать объявленные зависимости и требования модулей.
- **FR-012**: Система MUST продолжать обход при встрече непарсибельного файла, фиксируя его в отчёте об ошибках, и не прерывать индексацию.
- **FR-013**: Система MUST поддерживать инкрементальную переиндексацию по признаку изменения файла и удалять из индекса записи исчезнувших файлов.
- **FR-014**: Система MUST принимать путь к ядру и путь к файлу индекса как конфигурацию, без захардкоженных значений, и MUST допускать добавление дополнительных корней индексации сверх ядра без изменения кода.

#### Документация

- **FR-015**: Система MUST получать перечень страниц документации из карты сайта и уважать ограничения `robots.txt`.
- **FR-016**: Система MUST кэшировать загруженные страницы и не перезапрашивать неизменившиеся при повторном запуске.
- **FR-017**: Система MUST выдерживать паузы между запросами к сайту документации.
- **FR-018**: Система MUST хранить для каждой страницы URL, раздел, заголовок, текстовое содержимое и дату загрузки.
- **FR-019**: Система MUST выделять из текста упоминания версий вида «начиная с версии X.Y» и сохранять их как справочный признак, не как достоверную версионную привязку.
- **FR-020**: Сбор документации MUST работать через прямые HTTP-запросы, поскольку штатный механизм загрузки веб-страниц к целевому домену заблокирован сетевой политикой.

#### Инструменты для агента

- **FR-021**: Система MUST предоставлять поиск символа по полному или короткому имени с возможностью фильтрации по модулю.
- **FR-022**: Система MUST предоставлять получение сигнатур методов конкретного класса.
- **FR-023**: Система MUST предоставлять получение ORM-схемы сущности.
- **FR-024**: Система MUST предоставлять получение списка событий модуля.
- **FR-025**: Система MUST предоставлять получение параметров компонента.
- **FR-026**: Система MUST предоставлять проверку существования метода в текущей сборке с однозначным ответом и указанием модуля и версии.
- **FR-027**: Система MUST предоставлять полнотекстовый поиск отдельно по коду ядра и по документации.
- **FR-028**: Каждый ответ любого инструмента MUST содержать модуль-владелец, его версию и версию сборки, к которой относится индекс.
- **FR-029**: Ответы MUST быть компактными — сигнатура, путь и номер строки вместо содержимого файлов — MUST ограничивать число результатов и поддерживать запрос следующей порции.
- **FR-030**: При расхождении между кодом и документацией система MUST отдавать приоритет коду и явно помечать расхождение в ответе.
- **FR-031**: Система MUST обнаруживать и сообщать, что индекс устарел относительно текущего состояния ядра.
- **FR-032**: Полнотекстовый поиск MUST корректно обрабатывать запросы на кириллице.
- **FR-033**: Система MUST различать устаревшее процедурное API и современное объектное и помечать первое как устаревшее.

### Key Entities

- **Снимок сборки** — состояние ядра на момент индексации: версия сборки, дата версии, путь корня, время индексации, отчёт об ошибках разбора.
- **Модуль** — единица поставки Битрикса: код модуля, версия, дата версии, зависимости. Владеет всеми нижеперечисленными сущностями.
- **Символ** — класс, интерфейс или трейт: полное имя, вид, родитель и реализуемые интерфейсы, модуль, файл, строка, документирующий комментарий, признак устаревания.
- **Метод** — операция символа: имя, видимость, модификаторы, параметры, тип возврата, файл, строка, документирующий комментарий.
- **ORM-сущность** — привязка символа к таблице: имя таблицы, набор полей с типами, обязательностью и связями, признак полноты извлечения.
- **Событие** — точка расширения: имя, модуль, места вызова, передаваемые параметры.
- **Компонент** — переиспользуемый блок: идентификатор, параметры с типами и значениями по умолчанию, описание.
- **REST-метод** — публикуемая наружу операция: имя, модуль, привязанный обработчик.
- **Страница документации** — единица концептуальной документации: URL, раздел, заголовок, текст, дата загрузки, извлечённые упоминания версий.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На контрольной выборке из 50 реально существующих классов и методов ядра инструмент возвращает корректную сигнатуру и корректную версию модуля не менее чем в 95% случаев при сверке с исходниками.
- **SC-002**: 100% ответов инструментов содержат модуль-владелец и его версию.
- **SC-003**: На контрольной выборке из 30 заведомо несуществующих имён система в 100% случаев отвечает «не найдено» и ни разу не возвращает догадку.
- **SC-004**: Точечный запрос по имени символа возвращает результат менее чем за 1 секунду.
- **SC-005**: Полная индексация ядра выполняется одной командой без ручных шагов; повторный запуск без изменений в ядре занимает не более 10% времени полной индексации.
- **SC-006**: Индекс представляет собой один переносимый файл, пригодный к копированию на другую машину и использованию без переиндексации.
- **SC-007**: Типичный ответ инструмента укладывается в 2000 символов, что позволяет агенту задать несколько вопросов подряд без переполнения контекста.
- **SC-008**: Сбор документации получает все страницы из карты сайта без блокировок со стороны сайта; повторный запуск не выполняет повторных загрузок неизменившихся страниц.
- **SC-009**: Доля файлов ядра, которые не удалось разобрать, не превышает 1% и полностью зафиксирована в отчёте об ошибках.
- **SC-010**: Разработчик, обновивший ядро, приводит индекс в актуальное состояние одной командой, не читая документацию проекта.

## Assumptions

- Ядро доступно локально на чтение по настроенному пути и обновляется штатным апдейтером Битрикса; переиндексация запускается разработчиком вручную, автоматическое отслеживание изменений не требуется.
- Индекс используется локально одним разработчиком рядом с его агентом; многопользовательский сетевой доступ и совместное использование индекса вне области.
- Документация русскоязычная; поддержка других языков не требуется.
- Машина, на которой запускается сбор документации, имеет доступ в интернет; штатный механизм загрузки веб-страниц к целевому домену заблокирован, прямые HTTP-запросы проходят.
- Взаимодействие агента с сервером происходит локально в рамках сессии агента; удалённый хостинг сервера не предполагается.
- Индекс доступен только на чтение со стороны агента; изменение кода ядра через MCP не предусматривается.

### Предрешённые технические ограничения (вход для фазы планирования)

Эти решения приняты до написания спецификации и не подлежат пересмотру на фазе планирования:

- Извлечение данных из PHP выполняется полноценным разбором синтаксического дерева, а не регулярными выражениями, чтобы корректно обрабатывать пространства имён, трейты и наследование.
- Индекс хранится в единственном файле встраиваемой БД с поддержкой полнотекстового поиска.
- Индексатор и сервер — раздельные компоненты, связанные через файл индекса; индексатор реализуется на PHP, сервер — на TypeScript с официальным MCP SDK.
- Доступный тулчейн: PHP 8.4.4, Composer 2.8.6, Node 22.21, Python 3.14.

## Out of Scope

- Справочники `dev.1c-bitrix.ru/api_help/`, `dev.1c-bitrix.ru/api_d7/` и `apidocs.bitrix24.ru` — решение принято осознанно, в этой итерации не индексируются.
- Хранение нескольких снимков ядра одновременно и сравнение API между версиями ядра.
- Семантический поиск на векторных представлениях.
- Индексация кастомного кода проекта в каталоге `local` (около 5000 PHP-файлов и порядка 30 собственных модулей). Не входит в эту итерацию, однако **FR-014** требует, чтобы добавление дополнительного корня индексации было вопросом конфигурации, а не переработки.
- Выполнение кода, запросы к живой базе данных Битрикса и любые изменяющие операции.
