# Implementation Plan: MCP-сервер по ядру 1С-Битрикс с версионной привязкой

**Branch**: `001-bitrix-core-mcp` | **Date**: 2026-08-12 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-bitrix-core-mcp/spec.md`

## Summary

Инструмент строит поисковый индекс по установленной сборке Битрикса и отдаёт его ИИ-агенту через MCP так, что каждый факт сопровождается модулем-владельцем и его версией. Задача — убрать основную причину ошибок агента: уверенные утверждения об API, взятые из смеси разных версий продукта.

Два компонента, связанные одним файлом SQLite: индексатор на PHP разбирает 67 836 файлов ядра через AST и пишет индекс; MCP-сервер на TypeScript читает его и обслуживает десять узких инструментов. Версионная атрибуция вшита в схему данных, а не обеспечивается дисциплиной кода — отдать факт без версии структурно невозможно.

Фаза исследования изменила два проектных решения по сравнению с исходными предположениями и вскрыла дефект, который иначе попал бы в поставку незамеченным. Подробности — в [research.md](./research.md), кратко:

- **Найден режим тихой потери данных.** 41% файлов ядра (27 652 из 67 835) открываются коротким тегом `<?`. При `short_open_tag=Off` (умолчание в целевом окружении) парсер молча отдаёт такой файл как HTML: ни ошибки, ни исключения, ноль объявлений. На выборке 3000 файлов так терялось 2122 файла и 15% классов. Индексатор обязан отказываться стартовать в этом режиме.
- **Параллелизм оказался не нужен.** Замер дал 952 файла/с, то есть около 52 секунд чистого разбора на все 212 МБ ядра в один поток. Исходное опасение о неприемлемой длительности не подтвердилось, и сложность многопроцессной записи в SQLite не оправдана.

## Technical Context

**Language/Version**: PHP 8.4.4 (индексатор), TypeScript на Node 22.21.1 (сервер)

**Primary Dependencies**: `nikic/php-parser` 5.8.0 (проверен на целевом ядре), `@modelcontextprotocol/sdk`, `better-sqlite3`

**Storage**: один файл SQLite. Запись через PDO SQLite 3.51.1, чтение через `better-sqlite3`. FTS5, токенизаторы `unicode61` и `trigram` — наличие проверено на обеих сторонах

**Testing**: PHPUnit для индексатора, `node:test` для сервера, контрактные тесты инвариантов из [contracts/mcp-tools.md](./contracts/mcp-tools.md), команда `verify` на контрольной выборке

**Target Platform**: локальная рабочая станция разработчика, macOS/Linux

**Project Type**: CLI-индексатор + MCP-сервер на транспорте stdio

**Performance Goals**: полная индексация не более 10 минут (измеренный разбор — 52 с, остальное на извлечение и запись); точечный лукап менее 1 с; типичный ответ не более 2000 символов

**Constraints**: ядро открывается только на чтение, код ядра не выполняется, к БД проекта обращений нет; `short_open_tag=On` обязателен; stdout принадлежит протоколу, диагностика только в stderr; штатный механизм загрузки веб-страниц к домену документации заблокирован сетевой политикой, нужен свой HTTP-клиент

**Scale/Scope**: 93 модуля, 67 836 PHP-файлов, 212.2 МБ, 827 ORM-классов, 1463 файла с `getMap()` (504 в fluent-стиле), 2414 файлов `.parameters.php`, 2320 `.description.php`, 144 псевдонима классов, 27 652 файла с коротким тегом, 112 страниц документации

## Constitution Check

*GATE: пройден до Phase 0, перепроверен после Phase 1.*

Конституция версии 1.0.0.

| Принцип | Как обеспечивается в проекте | Статус |
|---|---|---|
| **I. Ядро — источник правды** | Сервер отвечает только из индекса. Отказ `found: false` — штатный ответ, а не исключение. Похожие имена, если возвращаются, изолированы в поле `did_you_mean` с пометкой «догадка». Расхождение кода и документации отдаётся в `code_conflict` с приоритетом кода | ✅ |
| **II. Версионная атрибуция (NON-NEGOTIABLE)** | Каждая сущность связана с `module` через внешний ключ, `module` хранит версию. Конверт `provenance` обязателен в каждом ответе. `version_unknown` отделён от подстановки чужой версии. Контрактный тест №1 проверяет инвариант | ✅ |
| **III. Разбор, а не догадки** | Извлечение через AST `nikic/php-parser` с `NameResolver`. Обе формы `getMap()` разбираются структурно. Неразрешимые части помечены `is_resolved` / `is_complete` / `incomplete_reason`. Регулярные выражения применяются только к прозе документации, что принцип прямо разрешает | ⚠️ одно отклонение, см. Complexity Tracking |
| **IV. Экономия контекста** | Ответ — сигнатура, путь и строка вместо содержимого файлов. Десять узких инструментов вместо одного поиска. Умолчания `limit` подобраны под классы старого API. Усечение всегда явное через `truncated` и `total`. Контрактный тест №2 запрещает выдачу файла целиком | ✅ |
| **V. Устойчивая индексация** | Ошибка разбора файла не прерывает проход, накапливается в отчёте и в `snapshot.parse_error_count`. Полная сборка — одна команда. Транзакция на файл. Детерминированность обеспечивается однопоточностью и отсутствием обращений к внешнему состоянию | ✅ |
| **VI. Только чтение (NON-NEGOTIABLE)** | Загрузчик Битрикса не подключается, файлы `.parameters.php` не выполняются, к БД проекта обращений нет, файлы ядра открываются только на чтение, сервер открывает индекс в режиме read-only. Побочные эффекты — только файл индекса и кэш документации | ✅ |

**Отдельно о цене Принципа VI.** Запрет на выполнение кода делает извлечение параметров компонентов принципиально неполным: в реальных файлах `DEFAULT` вычисляется через `GetMessage()` и `COption::GetOptionString()`, то есть требует загруженного ядра и живой БД. Это не дефект реализации, а осознанно принятая цена. Неполнота выражена структурно через `is_default_resolved` и `unresolved_count`, поэтому Принцип III не нарушается: агент видит разницу между «значения нет» и «значение вычисляется в рантайме».

**Post-Design перепроверка**: после разработки схемы данных и контрактов нарушений не добавилось. Обязательность `provenance` и запрет на выдачу содержимого файлов вынесены в контрактные тесты, то есть проверяются автоматически, а не ревью.

**Structure Decision**: разделение на `indexer/` и `server/` следует не из вкуса, а из Принципа VI — разделение писателя и читателя должно быть видно в структуре каталогов, а не держаться на договорённости. Граница между ними — файл индекса и версия схемы в `snapshot.schema_version`: сервер отказывается читать индекс несовместимой версии вместо того, чтобы отдавать неверно истолкованные данные.

Каталог `Preflight/` вынесен отдельно от `Core/` намеренно: проверка `short_open_tag` должна выполняться до открытия БД и до обхода файлов, и её расположение в дереве отражает это требование к порядку.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| Принцип III: `api_style` (`legacy` / `d7`) определяется эвристикой по форме имени, а не разбором | Достоверные сигналы покрывают не всё: `@deprecated` есть в 751 файле, `CAll*` — 184 объявления, но множество классов старого API (`CIBlockElement`, `CEventMessage`) не помечены никак. Без эвристики агент не отличит поколение API у большинства старых классов, а это одна из двух главных причин ошибок | Ограничиться только достоверными сигналами — оставляет основную массу старого API неразмеченной и не решает исходную задачу. Отклонение ограничено тем, что `api_style` хранится **отдельной колонкой** от `is_deprecated` и в ответах помечается как эвристика: догадка остаётся отличимой от факта, чего Принцип III и требует по сути |
| Два языка в одном репозитории | Решение заказчика, принято до планирования. Обосновано технически: точный разбор PHP требует PHP-парсера, зрелый MCP SDK — TypeScript | Одноязычный вариант на TypeScript потребовал бы tree-sitter, который даёт синтаксис без семантики и не разрешает трейты и импорты — это прямо запрещено Принципом III |

## Открытые вопросы из чеклиста спецификации

Чеклист требований отметил три требования без собственного сценария приёмки. Решения:

- **FR-011 (зависимости модулей)** — извлечение сохраняется, стоит одно чтение файла на модуль. Данные складываются в `module_dependency`, но в этой итерации ни один инструмент их не отдаёт. Решение о выделении отдельного инструмента откладывается до появления запроса; таблица заполняется, чтобы не переиндексировать ядро ради неё позже.
- **FR-019 (упоминания версий в тексте документации)** — извлекаются в `doc_page.version_mentions` и возвращаются инструментом `bitrix_search_docs` как справочное поле. Явно НЕ используются для суждений о наличии символа в сборке: это нарушило бы Принцип I.
- **FR-033 (различение поколений API)** — закрыто через `api_style` с зафиксированным выше отклонением от Принципа III и через `is_deprecated` с текстом пометки.
