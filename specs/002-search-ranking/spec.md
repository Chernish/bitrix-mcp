# Feature Specification: Ранжирование полнотекстового поиска

**Feature Branch**: `002-search-ranking`

**Created**: 2026-08-22

**Status**: Complete

**Input**: User description: "улучшить ранжирование и поиск: OR-склейка слов выдаёт шум по любому одиночному совпадению; слова короче 2 символов теряются"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Полные совпадения выше частичных (Priority: P1)

Агент ищет «send mail event» в коде ядра. Сейчас запрос из трёх слов склеивается
через ИЛИ, и верх выдачи занимают документы, совпавшие с одним случайным словом
(например, везде повторяющимся «event»). Агент получает нерелевантную выдачу и
тратит контекст на её разбор.

После изменения документ, содержащий ВСЕ слова запроса, всегда стоит в выдаче
выше документа, совпавшего только с частью слов. Среди документов с одинаковым
числом совпавших слов выше стоит тот, чьи совпадения весомее (плотность и
близость совпадений).

**Why this priority**: это ядро проблемы — без него поиск остаётся шумным при
любых остальных улучшениях.

**Independent Test**: выполнить поиск многословным запросом на индексе целевого
ядра и убедиться, что первый результат содержит все слова запроса.

**Acceptance Scenarios**:

1. **Given** индекс с документами A (содержит все 3 слова запроса) и B (содержит
   1 слово), **When** выполняется поиск всеми тремя словами, **Then** A стоит
   в выдаче выше B.
2. **Given** запрос, по которому нет ни одного документа со всеми словами,
   **When** выполняется поиск, **Then** возвращаются документы с частичными
   совпадениями, упорядоченные по числу совпавших слов — поиск не вырождается
   в пустой ответ.
3. **Given** два документа с одинаковым числом совпавших слов, **When**
   выполняется поиск, **Then** их взаимный порядок детерминирован и объясним
   весом совпадений.

---

### User Story 2 - Короткие значимые слова не теряются (Priority: P2)

Агент спрашивает про ORM или API. Слова короче двух символов отбрасываются до
поиска, и часть смысла запроса молча исчезает. Токены вроде «ORM», «IO», «d7»
несут смысл и должны участвовать в поиске.

**Why this priority**: заметность ниже, чем у ранжирования, но потеря осмысленных
токенов — та же категория дефекта «молчаливой потери», что запрещена конституцией.

**Independent Test**: поиск по запросу, содержащему короткий токен, находит
документы, где встречается только этот токен.

**Acceptance Scenarios**:

1. **Given** запрос, содержащий токен длиной 2 символа, **When** выполняется
   поиск, **Then** токен участвует в сопоставлении и его совпадение влияет
   на результат.
2. **Given** запрос, состоящий ТОЛЬКО из служебных знаков и стоповых обрывков,
   **When** выполняется поиск, **Then** система отвечает структурированным
   «не найдено», а не ошибкой.

---

### User Story 3 - Поведение единообразно у обоих поисков (Priority: P3)

`bitrix_search_code` (английские запросы) и `bitrix_search_docs` (русские)
сейчас дублируют логику построения поискового запроса копиями. Любое будущее
изменение правил придётся вносить дважды, и они неизбежно разойдутся.

**Why this priority**: снижение риска регрессий; пользовательской ценности
само по себе не добавляет, но защищает первые две истории.

**Independent Test**: оба инструмента отвечают на эквивалентные запросы
согласованным образом (одинаковые правила разбора и упорядочивания).

**Acceptance Scenarios**:

1. **Given** одинаковый набор правил разбора запроса, **When** оба инструмента
   получают эквивалентные запросы, **Then** оба применяют одни и те же правила:
   те же допустимые токены, тот же приоритет полных совпадений.

### Edge Cases

- Что происходит при запросе из одного слова? Выдача идёт по одному слову,
  правила ранжирования вырождаются в обычное упорядочивание по весу совпадения.
- Что происходит при запросе из более чем 10 слов? Длинные запросы не должны
  приводить к деградации времени ответа сверх бюджета инструмента (2000
  символов ответа сохраняется, время ответа остаётся интерактивным).
- Что происходит, когда слово встречается в запросе дважды? Дубликаты не должны
  увеличивать вклад слова в ранжирование.
- Что происходит при запросе, целиком состоящем из пунктуации? Ответ —
  структурированное «не найдено», а не сбой.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST ставить документ, совпавший со всеми словами запроса,
  выше любого документа, совпавшего лишь с частью слов.
- **FR-002**: Среди документов с равным числом совпавших слов система MUST
  упорядочивать выдачу по весу совпадений (релевантности), а при равенстве веса
  — детерминированно (стабильно от запроса к запросу).
- **FR-003**: Если ни один документ не содержит всех слов запроса, система MUST
  вернуть документы с частичными совпадениями вместо пустого ответа.
- **FR-004**: Токены запроса длиной от 2 символов MUST участвовать в поиске;
  их отбрасывание ДО появления поиска запрещено.
- **FR-005**: Число результатов и объём ответа MUST оставаться в существующих
  бюджетах инструментов (лимит постраничной догрузки, лимит размера ответа).
- **FR-006**: Каждый результат MUST по-прежнему нести модуль, версию модуля и
  версию сборки (Принцип II); изменение ранжирования MUST NOT затрагивать
  атрибуцию фактов.
- **FR-007**: Правила разбора запроса и упорядочивания выдачи MUST быть общими
  для обоих поисковых инструментов, а не продублированными.
- **FR-008**: Запросы, состоящие только из пунктуации или не дающие допустимых
  токенов, MUST возвращать структурированный ответ «не найдено» с причиной.
- **FR-009**: Ранжирование MUST быть воспроизводимым: одинаковый запрос к
  одинаковому индексу даёт одинаковый порядок результатов.

### Key Entities *(include if feature involves data)*

- **Поисковый запрос**: текст агента; разбирается на токены, очищается от
  синтаксических символов, дедуплицируется.
- **Результат поиска**: существующая структура (символ/страница + provenance);
  дополняется внутренним порядком, но НЕ новыми обязательными полями в ответе.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На контрольном наборе не менее 20 реальных многословных запросов
  к целевому ядру документ, содержащий все слова запроса, входит в первую
  пятёрку выдачи не менее чем в 90% случаев, где такой документ существует.
- **SC-002**: Ни один запрос из контрольного набора не возвращает пустой ответ,
  если в индексе есть хотя бы одно частичное совпадение.
- **SC-003**: Время ответа каждого из двух поисковых инструментов остаётся
  в пределах существующего бюджета (не хуже текущего более чем на 20%).
- **SC-004**: Размер ответа укладывается в существующий бюджет в 2000 символов
  для всех контрольных запросов.
- **SC-005**: Повторный прогон контрольного набора даёт идентичный порядок
  выдачи (детерминированность).

## Assumptions

- Контрольный набор запросов составляется вручную по типовым задачам Битрикс-
  разработки («отправка почтового события», «права доступа», «кеш инфоблока») —
  по 20+ запросов, и хранится в тестах как фикстура.
- Изменение касается только порядка и состава выдачи; схема индекса и формат
  ответа (включая provenance) не меняются, версия схемы БД не поднимается.
- Семантический/векторный поиск вне области этой спеки: улучшается только
  лексический полнотекстовый поиск.
- Расширенная индексация официальной документации docs.1c-bitrix.ru с
  извлечением примечаний о версиях ядра оформляется отдельной следующей
  спецификацией; базовый поиск по уже собранным концептуальным страницам входит
  в эту работу только как потребитель общей логики ранжирования.
