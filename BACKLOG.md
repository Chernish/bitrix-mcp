# Бэклог

## История и выбор версий ядра Битрикса

**Статус:** реализовано
**Объём:** отдельная итерация — хранение снимков, CLI, конфигурация MCP, контракты и тесты.

### Проблема

До внедрения версионности `index.sqlite` содержал один снимок ядра. `make update` заменял его текущим состоянием: версия сборки и версии модулей сохранялись, но предыдущая сборка переставала быть доступной для запросов и отката.

### Цель

Сохранять проиндексированные версии ядра и позволять явно выбирать снимок для работы MCP без смешивания фактов из разных сборок.

### Требуемое поведение

- После обновления предыдущий снимок остаётся доступен наряду с новым.
- Можно получить список снимков с `SM_VERSION`, датой сборки, датой индексации, корнем ядра и revision документации.
- Можно явно выбрать активный снимок для MCP-подключения; выбор версии в отдельном запросе проектируется отдельно и не должен приводить к смешиванию снимков.
- Каждый ответ по-прежнему содержит однозначный `provenance`: идентификатор снимка, `SM_VERSION`, модуль и версия модуля.
- `stale` вычисляется относительно выбранного снимка и текущего локального ядра; архивный снимок не должен незаметно выдаваться за актуальный.
- Существующая настройка через `BITRIX_MCP_INDEX` продолжает работать без обязательной миграции конфигурации.
- Незавершённое или неуспешное обновление не повреждает ни активный, ни архивные снимки.
- Есть управление хранением: просмотр занимаемого места и явное удаление архивных снимков без автоматической потери истории.

### Предпочтительный вариант реализации

Хранить независимые SQLite-файлы снимков и атомарно переключать активный указатель после успешной индексации. Это сохраняет текущие внешние ключи, FTS и проверки схемы, не требуя добавлять `snapshot_id` во все таблицы и запросы. Альтернативу с несколькими снимками в одной БД рассмотреть только после оценки стоимости изменения всех контрактов и миграции существующего индекса.

### Критерии приёмки

1. После перехода с версии A на версию B MCP может отвечать на запросы к обеим версиям по явному выбору пользователя.
2. Контрольный символ с разными сигнатурами в A и B возвращает данные только из выбранного снимка с правильными версиями модулей.
3. Без явного выбора сохраняется текущее поведение: используется активный снимок последней успешной индексации.
4. Прерванное обновление не меняет активный снимок и не оставляет частичный снимок доступным как готовый.
5. Повторная индексация одинаковой `SM_VERSION` не перезаписывает историю молча; такие снимки различаются однозначно.
6. Покрыты CLI, конфигурация сервера, `bitrix_index_status`, поиск, чтение документации, provenance, откат и удаление архива; выполнен smoke-тест минимум с двумя реальными версиями ядра.
